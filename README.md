## 当前状态

- 版本：MVP `v0.12.0`
- 形态：移动优先、响应式单页 HTML/CSS/JavaScript，桌面 / iPad / 手机三档断点自适应（参考「数学实验室」与「谷歌推广模拟器」的 UI/UX）
- 数据：脱敏模拟数据
- 外部依赖：无（教学引擎与经验本纯前端，无后端）
- 自动化测试：有（jsdom 真实 DOM 烟雾测试；`verify_lab.js` 现有 **73 项断言**，覆盖 7 关重排后的文案/词典/坐标/拖动联动/演示、预测决策链因果关系、金钱换算、撤销重做、反剧透、坐标轴单调性，以及 v0.12 新增的图内标注零重叠、画布利用率、坐标轴冻结、事件轨点击跳转——测试基建同时修了一个真问题：以前 draw() 在 jsdom 下画布尺寸恒为 0，绘制代码从未被真正执行过）
- 核心功能：
  - **「判断训练」系统（本版核心）**：顶部 Tab「教学训练 / 自由沙盘 / 动画实验室」切换。教学训练由 8 章必修 + 3 章选学组成，每章统一走「观察 → 判断 → 承诺理由+信心 → 看模拟结果 → 复盘归因 → 提炼一条个人规则」六步经验循环；不是只教概念公式，而是训练「怎样形成判断、怎样从错误中积累经验」。
  - **Forecast 经验本**（localStorage，key `sku_forecast_journal_v1`）：首页展示已完成循环数、高估 / 低估 / 较准确次数、最常犯错根因；同一章重做会覆盖旧记录，留下成长轨迹。
  - **四维度评分**：数据观察 / 逻辑依据 / 数值偏差 / 信心校准，不是只看对错。
  - **沙盘解锁**：完成 ≥ 3 次完整经验循环才解锁「自由沙盘」（原模拟器），否则显示遮罩与还需几次的提示。
  - 自由沙盘：**五个真实场景预设**（EU 稳定 / UK 黑五 / 新品首单 / EOL 清库 / 促销防守）、参数调整、180 天库存模拟、经营诊断、时间轴、库存曲线、四个快捷动作；「真实备货公式」面板（平均日销 / 当天备货量 / 红绿线 / 补货触发日，对齐《销售预测培训》）。
  - **🎬 动画实验室（v0.6 新增 / v0.7 重做为「搭积木式」/ v0.8 重做为「看图说话」）**：把 Forecast 理论做成可视化动画。**关键改进 v0.8：从 0 教起——先认坐标系，再教斜线/竖线/虚线/面积分别代表什么**。不再只丢一句"库存是一堆货"，而是像 MathLab 教学一样，每个元素都解释「为啥用这个几何形状」「为啥会动」「代表什么」。侧栏加**「📖 看图词典」**面板，随关卡逐步累计 12+ 条术语（📐 坐标图 / ━ 横线 / 📉 斜线 / 🔺 三角形 / ▨ 绿色填充 / ▏ 红竖线 / 📅 覆盖天数 / 🟣 紫虚线 / 🔻 绿箭头 / 🟥 红缺货区 / ⚌ 琥珀虚线 / 🟡 尖峰）。时间轴改中文「第 N 天/今天/60 天后」，加 y 轴刻度。7 关顺序 = 📦 库存本体 → 📉 每日卖出 → 🔴 售罄日 → 🟣 你的预测线 → 🟢 补货到货(提前期) → 🟠 安全库存线 → 🟡 促销尖峰；每关只高亮【新滑块】、告诉你从哪拖到哪、看什么，还有「看演示」自动帮你拖一遍。
  - **v0.5 经营进阶面板（本版新增，对齐 Govee 真实指标体系）**：
    - **GMV 拆解**：GMV = CR × AOV × Session；AOV = 单价 × 连单率；Session 拆成 Paid（Google/FB/AFF/Bing）+ Free（Organic/Direct）六路流量占比可视化。
    - **成本结构（指标逻辑五口子）**：采购价/GMV、头程（多海运少空运）、尾程（派等单）、营销（AS 控 ROI）、其它（仓储/平台/风控/关税）、收单，按 GMV 占比估算，与贡献利润并列交叉验证。
    - **ROI 与复购**：ROI = 销售额 ÷ 广告花费（广告承压该涨就涨、但要盯 ROI，对齐攻略 P6）；复购率 = 积分/EDM/售后流量贡献的长期 GMV。
    - **综合经营评分**：GMV 25% + 贡献利润 25% + 库存健康 20% + 缺货控制 15% + Forecast 准确 10% + 价格健康 5%（handoff 第 13 节公式），六维加权得分 + 总评颜色分级。
  - 教学章节（v0.5 已全面真实化）：8 章必修 + 3 章选学全部嵌入 Govee 真实方法论与引用锚点（forecast 攻略 P1–P8、业务逻辑.jpg、指标逻辑.jpg），从“教概念”升级为“教判断依据”。
- 交互增强：浅 / 深色主题切换（CSS 变量 + localStorage 记忆）、Material 风卡片与 KPI 网格、状态 pill、触控友好（最小点击目标 44px）、底部固定「重新模拟」按钮（移动端）

## GitHub 同步约定

远程仓库：

```text
https://github.com/Chris-zidi/sku-simulator-mvp
```

本项目采用“完成即同步”的默认规则：

1. 每次开发开始前先同步远程最新代码。
2. 每次完成一个可独立说明的改动后，先验证，再提交 Git。
3. 提交后默认推送到 GitHub，不需要项目负责人重复提醒。
4. 每次提交都要更新 `DEVELOPMENT_LOG.md`，记录版本、变更、验证结果和遗留问题。
5. 不提交未验证的半成品；跨电脑继续开发前，先确认本地分支与远程一致。

常用命令：

```bash
git pull --rebase
git status
git add <本次相关文件>
git commit -m "简明描述本次改动"
git push
```

## 版本管理

项目使用语义化版本：

```text
主版本.次版本.修订版本
MAJOR.MINOR.PATCH
```

- `PATCH`：修复、文案、样式微调和不改变产品范围的小改动。
- `MINOR`：向后兼容的新功能、新关卡或明显的模型能力提升。
- `MAJOR`：不兼容的架构、数据或核心玩法升级。

- `v0.12.0`：**图表可读性：y 轴贴合 + 顶部事件轨 + 标注零重叠（用户反馈"越到后面元素都挤在一起卡死了，是不是坐标系有局限，要不要换技术栈"）**。答案是不用换技术栈——D3/ECharts 一样要自己写避让，换栈只会丢掉已测引擎；真病因是 v0.10 埋的两个坑叠加：
  1. **y 轴按本关数据贴合，进关时冻结**：v0.10 的 yMax 硬编码 `max(12000, 库存+补货)`，库存只有 3000~5000 时严重过头，曲线被压进画布底部 26%~33%。改成 `niceTop()` 贴合本关数据，进关时算一次冻结（`freezeStageYAxis()`），拖任何滑块都不重新计算——完整保住"被拖动的维度必须锁死坐标域"那条铁律；库存冲出冻结的顶时只涨不缩。实测利用率：日销/售罄 32%→96%，补货/安全 26%→99%，预测/促销→100%。
  2. **顶部事件轨**：售罄/下单/到货/促销开始不再散落在曲线周围写死坐标，统一搬到画布顶部一条轨道，横向贪心避让，放不下自动换行；下单↔到货间画提前期括号；点事件标记播放头会跳过去，侧栏节点卡自动讲那一天。
  3. **图内标注瘦身 + 通用避让兜底**：长句子（少卖多少钱、占用多少资金、覆盖天数差距）移到本来就有位置的侧栏读数面板，图上只留短锚点；新增 `placeLabels()` 贪心避让算法，谁跟谁撞了就顺延（优先下移，会撞 x 轴日期文字就改上移），119 组合参数压力测试零重叠。
  4. 顺带修了一个新引入的测试基建 bug：`verify_lab.js` 里 `draw()` 因为画布尺寸恒为 0 从未被真正执行过，`fillText`/`measureText` 走的 mock 也接不住状态——这次一并修好，`verify_lab.js` 扩到 73 项断言，新增零重叠 / 画布利用率 / 坐标轴冻结 / 事件轨点击跳转专项验证。
- `v0.11.0`：**打通 Forecast 因果链（用户反馈"预测线拖了没反应，少赚钱怎么没体现，Forecast 这么早引入合适吗"）**。追代码发现比表象更深的问题：下单时机判断一直用真实日销算，`forecast` 滑块从头到尾不影响任何结果——现实里 Forecast 的全部意义恰恰是「你不知道真实需求，只能凭预测做决策」。
  1. **修「预测空转」根因 bug**：`simulate()` 拆成决策侧（何时下单/下多少，永远用 forecast 算）和结果侧（库存实际怎么消耗，永远用 demand 算）。预测准，两侧算的是同一个数，行为和以前完全一致；预测错了，决策就会跟着错——预测偏低 → 下单晚下单少 → 缺货带变大 → 少赚钱；预测偏高 → 下单早下单多 → 期末压一堆货 → 占用资金。
  2. **关卡重排**：补货、安全库存提到 Forecast 之前——前 5 关先假设「你预测得准」，Forecast 作为最后的「大 boss」关卡才把这个假设拿掉，而不是在第 4 关就摆出两条平行虚线让人费解。关卡序号判断从硬编码 `si>=N` 全部改成按元素名判断（`hasElement`/`stageIndexOf`），避免下次重排再踩坑。
  3. **金钱因果**：单件毛利口径取自 Govee 利润表真实数据（原价 79、成本 31），新增「少赚金额」「压仓占用」读数，图上补货缺口对应到 0 线上方的红色缺货带 + 金额标注，期末剩货画成右侧灰蓝色压仓块 + 金额标注。补货量从 Forecast 关起不再手动拖，改成按预测自动算——算错了，下单量本身就会跟着错。
  4. **修 header 高度测量 bug（v0.10 引入的回归）**：`--header-h` 曾被 `ResizeObserver` 在过渡态下测到一次偏高的值后再未更新，导致讲解区被压到只剩 20px 高。改用纯 CSS flex 布局（`.app.lab-mode`），高度由浏览器自己算，不再需要 JS 测量。
  5. **顶栏收窄**：教学训练/自由沙盘/动画实验室三个 Tab 从品牌行下方独立一行合并进同一行，省下的高度让给内容区；每个滑块的说明文案从单独一行并入标签同一行，进一步压缩纵向空间。
  6. 烟雾测试改用 `_debug.applyStage` 按元素名直接跳关（不再依赖点击次数推断位置），重排后仍全部通过，改到 **64 项断言**，新增预测决策链因果关系与金钱换算的专项验证。
- `v0.10.0`：**动画实验室体验重构（用户反馈"日销翻倍斜率反而变平、布局被切、没有解析/没有撤销、教学训练太乱"）**。这是一次结构性修复，核心问题是 v0.9.3 的坐标轴设计从根上算错了：
  1. **修坐标轴根因 bug**：v0.9.1~v0.9.3 的横轴按"覆盖天数"动态收窄、纵轴又被负库存尾巴撑开，两层自动缩放叠加互相抵消——实测日销从 26 拉到 60（翻倍多），屏幕斜率从 -1.108 变成 -0.537，售罄点位置基本不变，完全违背直觉。**改为横轴恒定 180 天、纵轴恒定按「期初库存+补货量」推算**（不受日销/负库存影响），现在日销 26→34→60 时屏幕斜率 -0.201→-0.263→-0.463 单调变陡、售罄点 100%→78.4%→44.4% 单调左移、三角形面积单调变小——变化终于是真的。
  2. **库存不再画成负数**：clamp 到 0，缺货改成 0 线上方的红色「缺货带」+「少卖约 M 件」标注，更符合业务直觉（现实里库存不会是负的）。
  3. **布局钉死视口**：`#labView` 高度按实测顶栏高度动态算 `calc(100vh - 头部高)`，左侧舞台（画布+读数+按钮）整块 flex 竖排、永不滚动、任何时候完整可见；右侧栏独立滚动，滑块固定在顶部常驻区，不用滚动就能看到。
  4. **关键节点解析**：新增侧栏「📍 现在图上发生了什么」卡片，跟着播放头/拖动的滑块实时讲清楚当前节点（发生了什么/为什么/怎么办）；第 3~7 关补齐图上直接标注（售罄公式、预测覆盖差距、提前期天数、下单节点、促销斜率放大倍数），不再只有第 2 关有解析。
  5. **反剧透**：未解锁的关卡 chip 只显示 🔒，不再提前显示后面关卡的名字。
  6. **撤销/重做/上一步/播放控制**：Ctrl+Z / Ctrl+Shift+Z 撤销重做（连续拖同一滑块合并成一条记录，切换到别的滑块立刻算新一步）；新增「← 上一步」按钮；画布下方播放条支持暂停/继续、拖动进度条跳到任意一天、逐天步进；**修复「一键模拟」演示完会把你自己调的参数覆盖成默认值的问题**——现在演示结束恢复你自己调过的值。

## 已确认的接手风险

1. 模拟循环使用 `day <= 180`，实际会计算第 0 天到第 180 天，共 181 个日周期；页面和文档描述为 180 天，需要统一时间口径。
2. 没有发生库存耗尽时，`physicalStockoutDay` 默认返回第 180 天，时间轴仍显示“库存耗尽”，可能误导用户。
3. “稳定款”期末库存约 54 件、覆盖约 2 天，但 `overstock` 规则仍将其判为积压风险，诊断文案与期末库存状态矛盾。**（v0.2.0 已缓解：积压判定改为期末覆盖 > 120 天，稳定款不再误判。）**
4. 库存曲线中的到货线没有对超过 180 天的 Lead Time 做贴边或隐藏处理，可能绘制到 SVG 画布之外。
5. 缺货区间宽度按首尾缺货日之差计算，单日缺货时宽度为 0；若缺货被到货暂时打断，连续区间也会被合并成一个长区间。
6. 核心模拟、诊断和 DOM 渲染全部耦合在一个 HTML 文件中，当前无法直接对业务函数建立稳定的单元测试。
7. 输入依赖浏览器控件的 `min`/`max`，模拟函数本身没有处理 `NaN`、负数或越界值。

## 建议接手顺序

1. 先确认“180 天”是 180 个日周期还是包含第 0 天的 181 个数据点。
2. 修复无缺货时的时间轴语义，以及 Lead Time 超出模拟期的图表边界。
3. 重新定义积压诊断，避免“期末库存健康但被判积压”的矛盾。
4. 抽离纯函数模拟引擎和诊断规则，并为交接文档列出的十个边界场景添加测试。
5. 完成桌面和手机尺寸的视觉与交互验收。
6. 验证稳定后，再决定是否重构为 React/TypeScript 工程。
