## 当前状态

- 版本：MVP `v0.4.0`
- 形态：移动优先、响应式单页 HTML/CSS/JavaScript，桌面 / iPad / 手机三档断点自适应（参考「数学实验室」与「谷歌推广模拟器」的 UI/UX）
- 数据：脱敏模拟数据
- 外部依赖：无（教学引擎与经验本纯前端，无后端）
- 自动化测试：有（jsdom 真实 DOM 烟雾测试，覆盖首页渲染、经验循环、四维度评分、经验本写入、沙盘解锁）
- 核心功能：
  - **「判断训练」系统（本版核心）**：顶部 Tab「教学训练 / 自由沙盘」切换。教学训练由 8 章必修 + 3 章选学组成，每章统一走「观察 → 判断 → 承诺理由+信心 → 看模拟结果 → 复盘归因 → 提炼一条个人规则」六步经验循环；不是只教概念公式，而是训练「怎样形成判断、怎样从错误中积累经验」。
  - **Forecast 经验本**（localStorage，key `sku_forecast_journal_v1`）：首页展示已完成循环数、高估 / 低估 / 较准确次数、最常犯错根因；同一章重做会覆盖旧记录，留下成长轨迹。
  - **四维度评分**：数据观察 / 逻辑依据 / 数值偏差 / 信心校准，不是只看对错。
  - **沙盘解锁**：完成 ≥ 3 次完整经验循环才解锁「自由沙盘」（原模拟器），否则显示遮罩与还需几次的提示。
  - 自由沙盘：三个预设、参数调整、180 天库存模拟、经营诊断、时间轴、库存曲线、四个快捷动作；「真实备货公式」面板（平均日销 / 当天备货量 / 红绿线 / 补货触发日，对齐《销售预测培训》）。
- 交互增强：浅 / 深色主题切换（CSS 变量 + localStorage 记忆）、Material 风卡片与 KPI 网格、状态 pill、触控友好（最小点击目标 44px）、底部固定「重新模拟」按钮（移动端）

本项目采用“完成即同步”的默认规则：

1. 每次开发开始前先同步远程最新代码。
2. 每次完成一个可独立说明的改动后，先验证，再提交 Git。
3. 提交后默认推送到 GitHub，不需要项目负责人重复提醒。
4. 每次提交都要更新 `DEVELOPMENT_LOG.md`，记录版本、变更、验证结果和遗留问题。
5. 不提交未验证的半成品；跨电脑继续开发前，先确认本地分支与远程一致。

## 版本管理

项目使用语义化版本：

```text
主版本.次版本.修订版本
MAJOR.MINOR.PATCH
```

- `PATCH`：修复、文案、样式微调和不改变产品范围的小改动。
- `MINOR`：向后兼容的新功能、新关卡或明显的模型能力提升。
- `MAJOR`：不兼容的架构、数据或核心玩法升级。

当前处于 MVP 阶段：

- `v0.1.0`：原始 MVP 与交接包基线。
- `v0.1.1`：建立 GitHub 自动同步、版本管理和开发记录规范。
- `v0.2.0`：对齐《销售预测培训》公式——全流程 Lead Time 119 天、新增真实备货公式面板（平均日销 / 当天备货量 / 红绿线 / 补货触发日），三预设形成 good/danger/warn 教学对比。
- `v0.3.0`：响应式 UI 重构——移动优先、桌面 / iPad / 手机三档断点自适应；新增浅 / 深色主题切换（记忆偏好）；Material 风卡片、KPI 网格、状态 pill；触控目标 ≥44px；参考「数学实验室」的友好章节卡片与「谷歌推广模拟器」的 Material 组件 + 主题切换，融合两者长处。已部署为手机 / iPad 可访问的在线演示。
- `v0.4.0`：从「纯模拟器」升级为「判断训练系统」——这是产品真正的差异化点。顶部 Tab「教学训练 / 自由沙盘」切换；教学训练由 8 章必修（Forecast 是什么 / Baseline / 未来变化 Checklist / 分段 Forecast / 库存覆盖与时间轴 / LT 与安全库存警戒线 / 补货量与经营动作 / 预测偏差与经验）+ 3 章选学（新品 / EOL 清库 / 真实周报复盘）组成，每章统一走「观察 → 判断 → 承诺 → 看结果 → 复盘 → 提炼规则」六步经验循环。引入 Forecast 经验本（localStorage）沉淀「我为什么这么判断、后来哪里错了、下次怎么改」的成长轨迹；四维度评分（数据观察 / 逻辑依据 / 数值偏差 / 信心校准）；完成 ≥3 次循环解锁自由沙盘。修正补货触发日公式（触发 = 库存覆盖天数 ≤ 客观 Lead Time + 安全库存天数），拆分 Lead Time / 安全库存 / 警戒覆盖期，准确率训练移到最后。新增 jsdom 真实 DOM 烟雾测试。

只有形成可复用或可交付的稳定节点时才创建 Git Tag，不要求每个普通提交都打 Tag。

## 已确认的接手风险

1. 模拟循环使用 `day <= 180`，实际会计算第 0 天到第 180 天，共 181 个日周期；页面和文档描述为 180 天，需要统一时间口径。
2. 没有发生库存耗尽时，`physicalStockoutDay` 默认返回第 180 天，时间轴仍显示“库存耗尽”，可能误导用户。
3. “稳定款”期末库存约 54 件、覆盖约 2 天，但 `overstock` 规则仍将其判为积压风险，诊断文案与期末库存状态矛盾。**（v0.2.0 已缓解：积压判定改为期末覆盖 > 120 天，稳定款不再误判。）**
4. 库存曲线中的到货线没有对超过 180 天的 Lead Time 做贴边或隐藏处理，可能绘制到 SVG 画布之外。
5. 缺货区间宽度按首尾缺货日之差计算，单日缺货时宽度为 0；若缺货被到货暂时打断，连续区间也会被合并成一个长区间。
6. 核心模拟、诊断和 DOM 渲染全部耦合在一个 HTML 文件中，当前无法直接对业务函数建立稳定的单元测试。
7. 输入依赖浏览器控件的 `min`/`max`，模拟函数本身没有处理 `NaN`、负数或越界值。

## 建议接手顺序

1. 先确认“180 天”是 180 个日周期还是包含第 0 天的 181 个数据点。
2. 修复无缺货时的时间轴语义，以及 Lead Time 超出模拟期的图表边界。
3. 重新定义积压诊断，避免“期末库存健康但被判积压”的矛盾。
4. 抽离纯函数模拟引擎和诊断规则，并为交接文档列出的十个边界场景添加测试。
5. 完成桌面和手机尺寸的视觉与交互验收。
6. 验证稳定后，再决定是否重构为 React/TypeScript 工程。
